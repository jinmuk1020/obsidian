# 디자인 사고 프로세스 (Design Thinking Process)

## 핵심 정의

> 디자인 사고 프로세스는 사용자의 실제 문제를 이해하고, 아이디어를 발산하며, 프로토타입과 테스트를 통해 해결책을 반복적으로 개선하는 인간 중심 문제 해결 접근법이다.

* **본질:** 정답을 미리 가정하지 않고, 관찰과 실험을 통해 문제와 해결책을 함께 학습한다.
* **맥락:** 제품 기획, 서비스 디자인, UX, 조직 혁신, 교육, 공공 문제 해결에서 사용된다.

## 작동 방식

디자인 사고는 보통 공감, 정의, 아이디어, 프로토타입, 테스트의 흐름으로 설명된다. 공감 단계에서는 사용자의 행동과 맥락을 관찰하고, 정의 단계에서는 발견한 문제를 설계 가능한 질문으로 정리한다. 아이디어 단계에서는 다양한 해결 가능성을 넓히고, 프로토타입 단계에서는 이를 빠르게 형태로 만든다. 테스트 단계에서는 사용자 반응을 통해 가정을 검증한다.

이 과정은 선형 절차가 아니다. 테스트에서 실패하면 아이디어 단계로 돌아가거나, 문제 정의 자체를 수정해야 할 수 있다. 디자인 사고의 강점은 실패를 늦게 발견하는 것이 아니라, 작고 빠른 실험을 통해 일찍 발견하게 만드는 데 있다.

* **메커니즘:** 사용자 이해 -> 문제 정의 -> 아이디어 발산 -> 시제품화 -> 검증과 반복.
* **구체적 예시:** 사용자가 결제 과정에서 불안해하는 이유를 관찰하고, 안내 문구와 화면 흐름을 프로토타입으로 테스트한다.
* **연계 프로세스:** Empathize -> Define -> Ideate -> Prototype -> Test.

## 실무적 의미

디자인 사고는 추상적인 창의성 교육이 아니라, 불확실한 문제를 다루기 위한 실무적 방법이다. 특히 문제의 원인이 명확하지 않거나, 사용자 요구가 말로 잘 드러나지 않거나, 여러 이해관계자가 얽힌 상황에서 유용하다.

팀 단위에서는 디자인 사고가 공통 언어가 된다. 조사, 문제 정의, 아이디어, 프로토타입, 검증을 분리하면 회의가 막연한 취향 논쟁이 아니라 근거와 실험 중심으로 바뀐다.

* **안정성:** 사용자 조사 없는 아이디어 발산은 공급자 중심 추측으로 흐르기 쉽다.
* **측정 가능성:** 문제 정의의 명확성, 프로토타입 테스트 결과, 개선 반복 횟수를 본다.
* **데이터 기준:** 인터뷰, 관찰, 로그, 피드백, 테스트 결과를 함께 사용한다.

## 주의할 점

디자인 사고를 포스트잇 워크숍이나 아이디어 회의로만 이해하면 얕아진다. 핵심은 공감과 검증이다. 사용자의 실제 맥락을 이해하지 않은 아이디어 발산은 그럴듯한 추측에 머물 수 있다.

또한 디자인 사고가 모든 문제의 만능 도구는 아니다. 기술적 제약, 법적 조건, 운영 비용, 조직 권한 같은 현실 조건과 결합되어야 실행 가능한 해결책이 된다.

* **관점의 한계:** 복잡한 시스템 문제는 디자인 사고만으로 해결되지 않을 수 있다.
* **상관관계 vs 인과관계:** 테스트에서 선호된 아이디어가 장기적으로 좋은 해결책이라는 보장은 없다.
