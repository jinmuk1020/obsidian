본 문서는 Ryan Watkins의 저서 **《Procedural Content Generation for Unity Game Development》** 소스 파일 내용을 바탕으로, 유니티 게임 개발 및 [[절차적 콘텐츠 생성 (PCG)|절차적 생성]](PCG)에서 핵심적인 역할을 수행하는 **딕셔너리(Dictionary, C# 자료구조)** 개념을 정리한 것입니다.

# 딕셔너리 (Dictionary, C# 자료구조)

## 한 문장 정의
딕셔너리는 **키-값 쌍(key-value pair)을 사용하여 데이터를 저장**하는 연관 배열(associative array)의 한 형태이며, 동적으로 데이터를 추가하거나 제거할 수 있는 C# 클래스입니다 [1].

## 상세 정의
딕셔너리는 일반적인 배열이나 리스트와 달리 인덱스에 음수가 아닌 정수 외에도 다양한 [[데이터|데이터]] 타입(예: 문자열, Vector2 등)을 사용할 수 있도록 설계되었습니다 [1, 2].
* **내부 구조:** 딕셔너리는 내부적으로 **배열을 감싸고 있는 클래스**입니다 [3].
* **동적 확장성:** 내부 배열이 가득 차려고 하면 시스템이 이를 자동으로 감지하여 더 큰 배열로 데이터를 다시 작성(Rewrite)하는 작업을 수행하므로, 개발자가 수동으로 크기를 관리할 필요가 없습니다 [3].
* **성능적 특징:** 데이터가 메모리에 산재하는 리스트와 달리 **빠른 검색(Lookup) 속도**를 보장하면서도, 크기가 고정된 배열의 한계를 극복한 효율적인 자료구조입니다 [3, 4].

## 문서 안에서의 맥락
본 소스에서 딕셔너리는 **'무한한 세계 생성(Generating an Endless World)'** 알고리즘을 구현하기 위한 최적의 도구로 등장합니다 [5, 6]. 플레이어가 탐험하는 타일의 좌표를 실시간으로 기록하고 추적함으로써, 이미 생성된 타일을 중복해서 만들지 않도록 관리하는 **'오브젝트 풀링(Object Pooling)'**의 근간이 됩니다 [7]. 또한, 플레이어의 **인벤토리 [[시스템 (System)|시스템]]**에서 아이템의 종류와 실제 데이터를 매핑하는 용도로도 사용됩니다 [8].

## 작동 메커니즘
1. **데이터 저장:** `Add(key, value)` 메서드를 통해 특정 키와 그에 대응하는 값을 한 쌍으로 묶어 저장합니다 (예: `myInventory.Add("Gold", 10)`) [3].
2. **존재 확인:** `Contains()` 메서드(또는 `ContainsKey`)를 제공하여 특정 키를 가진 데이터가 이미 존재하는지 즉각적으로 확인할 수 있으며, 결과값은 true/false로 반환됩니다 [2].
3. **데이터 참조:** 저장된 값은 배열과 유사한 인덱서 문법(`myInventory["Gold"]`)을 통해 직접 호출하여 읽거나 수정할 수 있습니다 [3].
4. **[[차원 축소|차원 축소]]:** 2차원 배열(Grid)을 관리할 때 `Vector2`를 키로 사용함으로써, 복잡한 2차원 배열 구조를 1차원적인 연관 관계로 단순화하여 처리할 수 있게 해줍니다 [2, 3].

## 설계/비즈니스상 중요도
* **성능 최적화:** 배열의 장점인 빠른 검색 속도와 리스트의 장점인 동적 추가 기능을 결합하여, 대규모 월드 데이터를 성능 저하 없이 관리할 수 있습니다 [1, 4].
* **[[시스템 (System)|시스템]] 안정성:** 타일 기반 게임에서 동일 좌표에 타일이 중복 생성되어 발생하는 논리적 오류나 리소스 낭비를 원천적으로 방지합니다 [9, 10].
* **개발 생산성:** 정수형 인덱스 대신 직관적인 키(좌표, 이름 등)를 사용하므로 코드의 가독성이 높아지고 데이터 관리가 용이해집니다 [2].

## 구체 사례
* **무한 월드 타일 추적:** `Dictionary<Vector2, Vector2>` (또는 `Dictionary<Vector2, TileType>`)를 생성하여 타일의 좌표를 키로 저장하고, 플레이어의 가시거리(Line of sight)에 들어온 타일이 이미 저장되어 있는지 확인합니다 [2, 11-13].
* **인벤토리 관리:** `Dictionary<String, Item>` 구조를 사용하여 "glove"나 "boot"와 같은 문자열을 키로 아이템 데이터를 저장합니다. 플레이어가 새로운 장비를 얻으면 딕셔너리 내의 기존 값을 새 데이터로 교체하여 인벤토리를 업데이트합니다 [8, 14].

## 실무 적용 방법
* **좌표 기반 중복 체크:** 타일을 배치하기 전 `if (!gridPositions.ContainsKey(tileToAdd))` 구문을 통해 해당 좌표가 딕셔너리에 있는지 먼저 검사하여, 없을 때만 새로 생성하고 딕셔너리에 추가합니다 [12, 15].
* **인벤토리 덮어쓰기:** 인벤토리 시스템에서 특정 슬롯(키)에 이미 데이터가 있다면 값을 교체하고, 없다면 새로 추가하는 방식으로 코드를 작성합니다 [14].
* **데이터 초기화:** 새로운 던전을 생성할 때마다 기존 딕셔너리 데이터를 `Clear()`하여 메모리를 관리하고 깨끗한 상태에서 생성을 시작합니다 [13].

## 흔한 오해와 주의점
* **메모리 사용량:** 딕셔너리는 내부 배열이 확장된 후에는 데이터를 삭제하더라도 해당 **최대 크기만큼의 메모리를 계속 점유**하고 있습니다 [1].
* **예외 발생:** 존재하지 않는 키를 검색하거나 참조하려고 하면 [[시스템 (System)|시스템]] 오류가 발생하여 게임이 멈출 수 있으므로, 반드시 존재 여부를 먼저 확인해야 합니다 [2, 16]. (리스트에 대한 경고를 딕셔너리 참조에도 동일하게 적용하는 맥락 - 추정)
* **오버헤드:** 클래스 자체의 추가적인 메서드들로 인해 아주 단순한 배열 데이터 구조보다는 약간의 오버헤드가 발생할 수 있습니다 [4].

## 관련 개념
- 배열(Array): 빠른 검색이 가능하지만 크기가 고정되어 동적 추가가 어려운 단순 자료구조 [4, 17].
- 리스트 (Linked List): 동적 추가는 자유로우나 데이터가 메모리에 흩어져 있어 검색 속도가 상대적으로 느린 자료구조 [18, 19].
- [[키-값 쌍 (Key-Value Pair)]]: 딕셔너리에서 데이터와 인덱스를 연결하는 기본 저장 단위 [1].
- [[오브젝트 풀링 (Object Pooling)]]: 딕셔너리로 타일 데이터를 추적하여 불필요한 재생성을 막는 관리 기법 [7].
- [[Vector2 (좌표)]]: 타일 기반 게임에서 딕셔너리의 키값으로 주로 사용되는 2D 위치 데이터 타입 [2].
